# Проблема та цінність

## Проблема

Люди витрачають час на планування раціону, складання списків покупок та регулярну закупівлю їжі.
Або забувають щось купити, або купують зайве, що потім псується. Бут з'їдає час, який можна було б
монетизувати інакше.

## Формулювання проекту

Система автоматичного постачання їжі клієнта за заданими умовами (дієта, бюджет, склад сім'ї) — по суті
**Food as a Service**: клієнт один раз задає правила, далі агент сам слідкує, щоб вдома завжди була
потрібна їжа, і сам ініціює дозамовлення.

## Цінність для клієнта

Головна метрика — **мінімум часу, витраченого на постачання їжею**. Не економія грошей як основна
цінність (хоча це бонус), а економія часу та когнітивного навантаження на побутові рішення.

## Цільова аудиторія

Remote-працівники та зайняті люди, у яких вартість години явно вища за час, який пішов би на
готування/закупівлю/планування. Платоспроможний сегмент, готовий платити за делегування буту.

## Цінність для «Сільпо»

- Переведення разових офлайн-покупок їжі в **підписну модель**
- Можливість **пушити високомаржинальні позиції** всередині автоматично сформованої кошики
- **Точна продуктова аналітика** та аналітика витрат на рівні домогосподарств
- Формування сегменту **онлайн-покупців** з передбачуваним патерном
- **Крос-продажі** на цьому сегменті: спортивне харчування (use case мас-набору), кінопопкорн під
  вечір п'ятниці, потенційно квитки до кіно (але тут конфлікт інтересів з фудкортом кінотеатру —
  див. «Відкриті питання»)

# Як пітчимо журі

1. **Проблема** — 30 секунд: у зайнятих людей їжа вдома або закінчується не вчасно, або псується,
   бо ніхто не слідкує за балансом «потрібно / вже є».
2. **Рішення** — показуємо не чат-бота, а агента з пам'яттю та циклом дій: онбординг → перша
   закупівля → регулярні чек-іни → автоматичне коригування замовлення.
3. **Живе демо** — записуємо реальний виклик MCP tools (JSON-RPC лог або запис екрана):
   `silpo_find_products_batch` → `silpo_add_or_update_cart_products` → `silpo_get_time_slots`.
   Жюрі має побачити, що це реальний agentic flow, а не заскриптована презентація.
4. **Подвійна цінність** — окремо проговорюємо цінність для гостя (час) і окремо для «Сільпо»
   (підписка, маржинальні допродажі, аналітика, крос-сейл). Це відрізняє нас від банального
   «ще один чат-помічник», чого організатори прямо просили уникати.
5. **Валідація та масштабування** — показуємо, як можна виміряти цінність (час до першого повторного
   замовлення, retention циклу чек-інів, % автоматичних confirm без правок) і куди це масштабується
   (спецрежими: блекаут, хвороба, спортивне харчування — тобто один двигун закриває багато сценаріїв життя).

# Список фіч та порядок імплементації

## Must have (ядро для демо)

1. Онбординг: збір дієти/бюджету/складу сім'ї + підтягування даних через MCP
   (`silpo_get_my_food_restrictions`, `silpo_get_my_family`, `silpo_get_my_online_orders`)
2. Генерація тижневого раціону + список покупок
3. Перша закупівля: збірка кошики через MCP + підтвердження користувачем
4. Цикл чек-інів (текст/войс) → дифінг з базовим набором → коригування наступного замовлення
5. Точка перезамовлення: дельта-замовлення, підбір слоту доставки, застосування бонусів

## Додаткові фічі (після ядра)

1. **Авто-підбір знижок** — підстановка товарів з активними промо (`silpo_get_promotions`) без втрати
   відповідності раціону
2. **Фільтрація за дієтою** — вегетаріанство/безглютенове/etc як постійний фільтр на підбір товарів
3. **Авто-внесення доставки в календар** — подія в Google Calendar на слот доставки
4. **Аналітика витрат** — динаміка чека, економія на промо, порівняння з звичайним офлайн-патерном
5. **Спецрежим «блекаут»** — при відключенні світла перемикання на позиції, які не потребують
   готування/холодильника, разове замовлення «гаряче на обід» через партнерів з готовою їжею

## Сценарні (продуктові) режими — це де-факто окремі user flows поверх одного двигуна

1. Разове замовлення «смачне під фільм у п'ятницю» (+ крос-сейл попкорну, див. відкриті питання)
2. Зміна профілю на «більш дієтичний» (наприклад мінус 200 ккал/день) без втрати структури раціону
3. Зміна профілю на «тільки український виробник» — фільтр за виробником на весь підбір
4. Медичний спецрежим — наприклад гастрит: тиждень щадного харчування → дієт-стіл № 5 → повернення
   до звичайного раціону за розкладом
5. Профіль «мас-набір» — збір додаткових параметрів (вага, ціль за калоріями/білком) та крос-продаж
   спортивного харчування

## Флагнута фіча (потрібно вирішити, чи робити)

1. **«Зменши чек на N-ну суму»** — економія як пряма мета. Ризиковано: підштовхує до продажу
   дешевших/менш маржінальних позицій, що може йти врозріз з інтересами «Сільпо» як партнера
   хакатону. Обговорити до реалізації.

# Відкриті питання

- **Як збирати дані користувача без ручного введення анкети?** Ручний ввід — поганий UX для цієї ЦА
  (люди платять саме за те, щоб не витрачати час). Напрямки: максимально тягнути з MCP
  (`silpo_get_my_family`, `silpo_get_my_food_restrictions`, `silpo_get_my_online_orders`,
  `silpo_get_my_favorites`) замість анкети; progressive profiling — збирати параметри поступово через
  естественні діалоги (чек-іни), а не однією формою; для спецрежимів (мас-набір, медичний) — коротке
  точкове опитування лише тоді, коли режим реально вмикається, а не заздалегідь.
- **Попкорн під реліз фільму** — гарна крос-сейл ідея («під вечір п'ятниці»), але зв'язка «фільм + їжа»
  потенційно розширюється до продажу квитків, що створює конфлікт інтересів з фудкортом кінотеатру,
  якщо партнерство коли-небудь піде в цей бік. Тримаємо на увазі, не форсуємо на MVP.
- **Функція зменшення чека** (див. флагнуту фічу) — потрібно вирішити до реалізації, чи не суперечить
  це позиціонуванню перед організаторами.

# User Flows

## 1. Онбординг + перша закупівля (базовий цикл)

1. Користувач пише боту в Telegram, відповідає на кілька запитань: склад сім'ї, дієта, бюджет, що не любить
2. Агент підтягує через MCP те, що вже є в профілі «Сільпо» (сім'я, обмеження, історія замовлень),
   не перепитує те, що вже відомо
3. Агент генерує меню на тиждень → розгортає в список покупок
4. Агент шукає товари через `silpo_find_products_batch`, збирає кошику
5. Показує користувачеві повну кошику на підтвердження
6. Після підтвердження — зберігає це як «еталонний набір» (baseline)

## 2. Регулярний чек-ін (кожні ~3 дні)

1. Бот сам пише користувачеві: «як справи з їжею, що залишилося?»
2. Користувач відповідає текстом або голосовим
3. Агент розбирає відповідь у структурований список «залишилось / закінчується / немає»
4. Порівнює з очікуваним залишком за baseline, оновлює стан
5. Якщо продукт стабільно не чіпають кілька циклів підряд — позначає як кандидата на виключення
   з наступного плану

## 3. Точка перезаказу (кінець тижня / за тригером)

1. Настає день закупівлі (за розкладом) або критичний продукт закінчився раніше строку
2. Агент формує не весь список заново, а дельту — те, що реально потрібно докупити
3. Перевіряє наявність, шукає заміни через `silpo_get_replacements`
4. Перевіряє активні акції (`silpo_get_promotions`), застосовує бонуси
5. Підбирає слот доставки під звичний патерн користувача
6. Показує зібране замовлення на підтвердження
7. Після підтвердження — оновлює календар (якщо фіча ввімкнена), фіксує правки як новий baseline

## 4. «Замов щось смачне на вечір п'ятниці зі знижками під фільм»

1. Користувач пише разовий запит, не за розкладом
2. Агент шукає товари за критерієм «снек/перекус» з активними промо (`silpo_get_promotions`)
3. Формує міні-кошику (окремо від основного раціону, не чіпаючи baseline)
4. Показує на підтвердження з позначкою ціни/економії
5. (опційно, стретч) пропонує додати попкорн, якщо є сигнал про реліз фільму

## 5. «Гаряче на обід у блекаут»

1. Користувач повідомляє про блекаут (або це фіксований режим, який він вмикає заздалегідь)
2. Агент фільтрує пошук товарів за критерієм «не потребує готування/холодильника» — готова їжа,
   консерви тощо
3. Збирає міні-замовлення на найближчий підходящий слот доставки
4. Показує на підтвердження

## 6. «Зроби раціон більш дієтичним, мінус 200 ккал/день»

1. Користувач дає команду змінити параметр раціону
2. Агент перераховує поточний/наступний план меню під новий калораж, зберігаючи структуру прийомів їжі
3. Формує оновлений список покупок під новий план
4. Показує дифф: що змінилося в списку порівняно з минулим разом
5. При наступному перезамовленні вже використовує оновлений профіль як норму

## 7. «Зменши чек на N-ну суму» (флагнута фіча)

1. Користувач задає цільову суму економії
2. Агент шукає дешевші аналоги / товари з акціями в межах вже обраного раціону
3. Показує: що замінено, на скільки зекономлено, що залишилось без змін
4. Користувач підтверджує або відкочує конкретні заміни

## 8. «Переходимо тільки на продукти від українського виробника»

1. Користувач вмикає фільтр у профілі
2. Агент позначає прапор `only_ua_producer = true` в профілі
3. При кожному наступному пошуку товарів (звичайна закупівля, разові запити) фільтр застосовується
   автоматично
4. Якщо для конкретної позиції немає українського аналога — агент явно повідомляє про це при показі
   кошика, не підставляє тихцем імпортний товар

## 9. «Захворів, гастрит» → дієт-стіл № 5 → звичайний режим

1. Користувач повідомляє про хворобу / вводить медичний режим
2. Агент тимчасово перемикає профіль на щадний раціон (перший тиждень), далі на дієт-стіл № 5
3. Увесь цей час звичайний baseline не використовується, але зберігається у фоні
4. Після закінчення терміну (або за командою «я в порядку») агент повертається до звичайного профілю
5. Кожна стадія — окремий міні-план з власним списком покупок та підтвердженням

## 10. «Мас-набір, порахуй дієту під мене»

1. Користувач запитує режим набору маси
2. Агент запитує бракуючі параметри: вага, ціль за калоріями/білком (не можна порахувати без них —
   короткий уточнюючий діалог)
3. Генерує висококалорійний/високобілковий план харчування
4. Формує список покупок, включаючи (стретч) крос-пропозицію спортивного харчування, якщо є інтеграція
5. Показує кошик на підтвердження
